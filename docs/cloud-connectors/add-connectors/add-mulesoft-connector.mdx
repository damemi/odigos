Add a MuleSoft Cloud Connector to manage **one Anypoint organization** (business group). The connector runs in the Central cluster, discovers Mule 4 applications and Omni Gateways in every environment its Connected App can see, and can instrument CloudHub 2.0 applications and Managed Omni Gateways when you create Sources.

<Note>
  [Enable Cloud Connectors](/cloud-connectors/enable)
  before you add a connector.
</Note>

## How instrumentation works

Mule applications are instrumented with Mule's **Direct Telemetry Stream**, the runtime's built-in OpenTelemetry exporter. Odigos turns it on by setting `mule.openTelemetry.*` application properties on the deployment. There is no agent to install and no image to rebuild.

- Requires **Mule runtime 4.11 or later** (metrics need 4.12 or later) and an Anypoint **Advanced or Titanium** subscription. On other tiers the properties are accepted but nothing is exported.
- Changing an application's properties makes the platform **redeploy it** (rolling update). Odigos only changes an application when its properties differ from what they should be, and never while a previous update is still rolling out.
- Turning on Direct Telemetry Stream **turns off Anypoint Monitoring's Telemetry Exporter** for that application. Any export you configured there stops.
- Odigos does not overwrite Direct Telemetry Stream settings you configured yourself; such applications are reported with a conflict.

## Resource types

| Type | Discovery | Instrumentation |
| --- | --- | --- |
| `mulesoft.cloudhub2-app` (CloudHub 2.0 shared spaces) | Yes | Yes |
| `mulesoft.private-space-app` (CloudHub 2.0 private spaces) | Yes | Coming soon |
| `mulesoft.rtf-app` (Runtime Fabric) | Yes | Coming soon |
| `mulesoft.hybrid-app` (servers managed by Runtime Manager) | Yes | Configure on the server |
| `mulesoft.omni-gateway` (Omni Gateway, formerly Flex Gateway) | Yes | Managed gateways: yes. Self-managed: manual |

CloudHub 1.0 and Mule 3 applications are not discovered. Private space and Runtime Fabric applications are discovered, and a Source on one reports that instrumentation is not implemented yet; Odigos does not change them.

### API Manager metadata

An application that [API autodiscovery](https://docs.mulesoft.com/mule-gateway/mule-gateway-autodiscovery-overview) pairs with an API Manager instance carries that instance on its spans, as the resource attributes `mulesoft.api.id`, `mulesoft.api.asset.id` and `mulesoft.api.version`. Odigos pairs an application through the property that holds its API id (`api.id`, or any property whose name ends in `api.id`), so you can filter traces by the API they served.

- It needs the **View APIs Configuration** scope. Without it, applications are discovered and instrumented without the API attributes.
- The attributes are added in automatic mode. A pairing that appears or changes is a properties change, so the application redeploys once.

### Omni Gateway

Odigos instruments an Omni Gateway by turning on its **distributed tracing** with an OpenTelemetry provider that exports to your destination. The gateway's spans join the Mule application's trace, because Mule continues the W3C `traceparent` header it receives on an HTTP Listener.

- **Managed Omni Gateways** (run by MuleSoft on a CloudHub 2.0 space): Odigos sets the tracing configuration itself, and Gateway Manager redeploys the gateway to apply it. Odigos records the gateway's previous tracing settings and restores them when you disable the Source. A gateway that already has tracing turned on is reported with a conflict and left alone.
- **Self-managed gateways** keep their configuration on your hosts, which Odigos cannot reach. Use manual mode: Odigos publishes a Configuration resource to apply on the gateway, but cannot read it back, so it cannot confirm the gateway is instrumented.
- Odigos adds the tracing label `odigos.managed` to gateways it configures, and the instructions add `odigos.iac`. Labels are added to every span the gateway emits.

## Add the connector

<Steps>
  <Step title="Open Add connector and choose MuleSoft">
    In the Central UI, open Connections / Connectors and start **Add connector**. Choose **MuleSoft**, and pick the **control plane** your organization lives on: US (`anypoint.mulesoft.com`) or EU (`eu1.anypoint.mulesoft.com`).
  </Step>

  <Step title="Choose access level">
    **Discovery only** lists applications and lets you apply the instrumentation properties yourself. **Discovery + instrumentation** also lets Odigos set them. The UI shows the Connected App scopes each level needs.
  </Step>

  <Step title="Create the Connected App">
    In Anypoint Platform, open **Access Management → Connected Apps → Create app**, choose **App acts on its own behalf (client credentials)**, add the scopes the UI listed, and select the business groups and environments Odigos should see. Environments you leave out are not scanned.
  </Step>

  <Step title="Enter the organization and credentials">
    Enter the organization (business group) ID, and the Connected App's client ID and client secret. Odigos tests the connection before it creates the connector.
  </Step>
</Steps>

## Instrument applications yourself

With **Discovery only**, open a discovered application in Odigos to get the properties to apply, as a Runtime Manager properties block, a `mule-maven-plugin` snippet or an `anypoint-cli` command. Odigos fills in your destination's protocol and endpoints, the source name, the environment, organization and target type. Apply them and redeploy. Odigos reports the application as instrumented once it sees the `ODIGOS_IAC` property, and checks that what you applied matches: a wrong endpoint or service name is reported as partially instrumented, naming what to fix.

Both OTLP gRPC and OTLP/HTTP destinations work. Use OTLP/HTTP when the path from CloudHub to your collector only carries HTTPS.

On hybrid servers, Direct Telemetry Stream is configured with **server** properties in Runtime Manager, so it applies to every application on that server.
