Add a GCP Cloud Connector to manage **one Google Cloud project**. The connector runs in the Central cluster, discovers resources across every location in that project, and can instrument Cloud Run services when you create Sources.

<Note>
  [Enable Cloud Connectors](/cloud-connectors/enable)
  before you add a connector.
</Note>

## Resource types

| Type | Domain | Discovery | Instrumentation |
| --- | --- | --- | --- |
| `gcp.cloud-run` | Workload | Yes | Yes (Java, Python, Node.js, .NET) |
| `gcp.gke` | Compute platform | Yes | Coverage only; agent installation is not available |
| `gcp.gce` | Compute platform | Yes | Coverage only; agent installation is not available |

<Info>
  GKE clusters and Compute Engine instances are compute-platform types reported
  for coverage only. They are not offered by the access levels in the Create
  Cloud Connector UI. The UI configures Cloud Run discovery and instrumentation.
</Info>

## Add the connector

<Steps>
  <Step title="Open Create Cloud Connector and choose GCP">
    In the Central UI, open **Connections**, click **Create new**, and choose **Cloud Connector**. In the drawer, choose **GCP**.
  </Step>

  <Step title="Choose access level">
    Choose how much access this connector should have. The UI shows a **Policy preview** of the custom IAM role for the level you pick. The setup templates in the next step embed it and grant it to the connector's service account.

    <img
      src="/images/cloud-connectors/gcp-access-level.png"
      alt="Create Cloud Connector dialog with GCP selected and the Discovery + instrumentation access level showing a custom role policy preview"
    />

    <Tabs defaultTabIndex="1">
      <Tab title="Discovery only">
        The connector can list and read Cloud Run services and revisions but cannot change them or attach instrumentation.

        Use this when you want inventory and visibility first, or when a separate identity will handle instrumentation later.

        Typical permissions include:

        | Purpose | Permissions |
        | --- | --- |
        | Authentication / project access | `resourcemanager.projects.get` |
        | Cloud Run discovery | `run.services.list`, `run.services.get`, `run.revisions.list`, `run.revisions.get` |
      </Tab>
      <Tab title="Discovery + instrumentation">
        The connector can discover resources and instrument supported workloads. Prefer this for a full setup in one step.

        Includes all discovery permissions, plus Cloud Run instrumentation:

        | Purpose | Permissions |
        | --- | --- |
        | Update services | `run.services.get`, `run.services.update`, `run.operations.get` |
        | Act as runtime service account | **`iam.serviceAccounts.actAs`** |
        | Language detection (optional) | `artifactregistry.repositories.downloadArtifacts` (or `roles/artifactregistry.reader`) |

        <Warning>
          `iam.serviceAccounts.actAs` is required to update Cloud Run services that
          run as a runtime service account. Without it, instrumentation fails even
          when `run.services.update` is granted. Bind it in a custom role, or grant
          `roles/iam.serviceAccountUser` on the runtime service account.
        </Warning>

        Cloud Run instrumentation also requires an [OTLP destination](/cloud-connectors/instrument-workloads#add-an-otlp-destination) after the connector is online. That endpoint must be reachable **from Cloud Run**, because instrumented services export OTLP directly to it.
      </Tab>
      <Tab title="Custom">
        Pick which resource types may be discovered and which may be instrumented. The UI updates the **policy preview** to match your selections so the IAM role stays aligned with what verification will validate.

        Use Custom to discover Cloud Run services while keeping instrumentation self-managed, or to let Odigos manage instrumentation.
      </Tab>
    </Tabs>

    <Info>
      Use the policy preview as the source of truth for the custom role. This
      keeps connector access scoped — not blanket project owner. See
      [You control the access scope](/cloud-connectors/overview#you-control-the-access-scope).
    </Info>

    The gcloud script enables the Cloud Resource Manager, Cloud Run, Container, Compute, and IAM APIs. If you use Terraform or the Console, enable them in the project yourself. Then click **Next** to continue to **Setup credentials**.
  </Step>

  <Step title="Setup credentials">
    Use your already-authenticated gcloud CLI, Console, or Terraform workspace to provision the service account and grant its permissions. The provisioning session is separate from the service account key Odigos uses at runtime.

    On **Setup credentials**, enter the project ID and use **Service account key**. Choose **gcloud**, **Terraform**, or **Console** for the setup instructions. Templates embed the selected permissions policy and remain visible while you fill in the project details.

    #### 1. Enter Google Cloud project

    <ParamField path="GCP Project ID" type="string" required>
      The Google Cloud project that contains the resources Odigos should discover. Use the project ID (lowercase letters, digits and hyphens, 6–30 characters), not the project name or number.
    </ParamField>

    The UI also offers an optional **Connector name**.

    #### 2. Create the service account, role, and key

    <Tabs>
      <Tab title="gcloud">
        Run the script from the UI using your authenticated session in the target project. It writes `odigos-connector-role.yaml`, enables the APIs, creates the dedicated `odigos-connector` service account and `odigosCloudConnector` custom role, binds that role, and creates the JSON key. No separate policy file is required.
      </Tab>
      <Tab title="Terraform">
        Apply the snippet in a workspace authenticated to the target project. It creates the service account, custom role, binding, and key. Follow the UI commands to read the sensitive JSON output. Protect the state backend because it retains the key.
      </Tab>
      <Tab title="Console">
        Create a custom IAM role from the selected permissions policy, create a dedicated service account, grant it that role on the project, and create a JSON key for it.
      </Tab>
    </Tabs>

    You can also use an existing service account key if that account has the complete selected permissions. If an organization policy disables service account key creation, have your administrator resolve that restriction before using this authentication method.

    #### 3. Enter the service account key

    <ParamField path="Service Account Key (JSON)" type="string" required>
      Paste the complete JSON key for the service account with the required permissions in the target project.
    </ParamField>

    The key is stored in a Kubernetes Secret in the Central cluster — never in the connector spec.
  </Step>

  <Step title="Verify and create">
    Click **Verify & Create Connector**. Central runs connection checks, then writes the credentials Secret and creates the `OdigosCloudConnector` resource when verification succeeds.

    <Info>
      Verification covers access to the configured project and representative discovery
      reads for the selected resource types. It does not prove instrumentation writes
      or telemetry delivery. For **Discovery + instrumentation**, also ensure the
      instrumentation permissions from the policy preview (including
      `iam.serviceAccounts.actAs`) are granted before you create Sources.
    </Info>
  </Step>

  <Step title="Wait for Connected">
    After create succeeds, wait until the connector status is **Connected** and initial discovery has completed.
  </Step>
</Steps>

<Check>
  When the connector shows Connected, you can browse discovered workloads and
  start [instrumenting](/cloud-connectors/instrument-workloads).
</Check>
