---
title: 'Preload the Fargate Agents Image'
description: 'Mirror the Fargate agents image into a private registry instead of pulling it from the Odigos registry.'
sidebarTitle: 'Preload'
---

Every instrumented Fargate task pulls the same agents bundle each time it starts. It isn't baked into your task
image, and a failed pull blocks the whole task, because the application container waits for the `odigos-agent`
container to finish (`SUCCESS` dependency).

Most accounts need none of this. Preload the image only if your Fargate tasks run in a network that can't reach
the Odigos registry, or your organization requires every image your tasks pull to live in a registry you own.

<Info>
  The current release is **`v0.0.30`**. Use it as `<version>` below. The CDK package's version is the same
  as the image tag it uses by default (`@odigos/aws-cdk@0.0.30` stages `odigos-fargate-agents:v0.0.30`).
</Info>

<Tabs>
  <Tab title="Odigos registry (default)">
    By default, tasks pull `registry.odigos.io/odigos-fargate-agents:<version>`, a public multi-arch
    (amd64 and arm64/Graviton) image. The task's subnet needs outbound internet access (a public IP or NAT).

    There's nothing to configure. Odigos-managed instrumentation and the CDK construct use this image unless you
    override it, and CloudFormation snippets reference it until you change the `Image`.
  </Tab>

  <Tab title="Your own private registry">
    Mirror the image into a registry your task's execution role can already reach. For example, a private
    ECR repository in the same account:

    <Steps>
      <Step title="Create a repository">
        ```bash
        aws ecr create-repository --repository-name odigos-fargate-agents --region <region>
        ```
      </Step>

      <Step title="Authenticate Docker to your ECR registry">
        ```bash
        aws ecr get-login-password --region <region> \
          | docker login --username AWS --password-stdin <account-id>.dkr.ecr.<region>.amazonaws.com
        ```
      </Step>

      <Step title="Copy the image, preserving the multi-arch manifest">
        Use `docker buildx imagetools create` rather than `pull` and `push`. A plain pull fetches only your
        machine's architecture, so pushing it back would give Graviton (arm64) tasks an amd64 image that fails to start.

        ```bash
        docker buildx imagetools create \
          --tag <account-id>.dkr.ecr.<region>.amazonaws.com/odigos-fargate-agents:<version> \
          registry.odigos.io/odigos-fargate-agents:<version>
        ```

        <Tip>
          Pin `<version>` to a released tag instead of mirroring on a schedule. A mirror that follows a newer
          bundle changes what your tasks stage without a deploy, and with Odigos-managed instrumentation the
          connector expects the exact image it is configured with.
        </Tip>
      </Step>

      <Step title="Point instrumentation at your mirrored image">
        <Tabs>
          <Tab title="CloudFormation">
            Replace the `Image` on the `odigos-agent` container in your task definition with your mirrored
            tag, and put the same value in the `image` field of each container's `ODIGOS_IAC` — see
            [Instrument Fargate](/cloud-connectors/aws/workloads/fargate/instrument).
          </Tab>

          <Tab title="CDK">
            Pass your mirrored tag as `agentsImage` on the construct:

            ```typescript
            new OdigosFargateInstrumentation(this, 'Odigos', {
              destination: { httpEndpoint: 'https://otlp.example.com:4318' },
              agentsImage: '<account-id>.dkr.ecr.<region>.amazonaws.com/odigos-fargate-agents:<version>',
            });
            ```

            See [CDK reference: Fargate](/cloud-connectors/aws/cdk/fargate#the-agents-image).
          </Tab>

          <Tab title="Odigos-managed">
            The `connector-runtime` controller reads `CONNECTOR_AWS_FARGATE_AGENTS_IMAGE` and sets
            `ODIGOS_FARGATE_AGENTS_IMAGE` on every AWS connector it manages. The Central Helm chart has no value for
            it, so set it on the controller directly:

            ```bash
            kubectl set env deployment/connector-runtime -n odigos-central \
              CONNECTOR_AWS_FARGATE_AGENTS_IMAGE=<account-id>.dkr.ecr.<region>.amazonaws.com/odigos-fargate-agents:<version>
            ```

            <Warning>
              This overrides the agents image for **every** AWS connector the controller manages, so an image
              that is wrong or unreachable affects every instrumented Fargate service at once. The task
              execution role of each service needs `ecr:GetAuthorizationToken` plus
              `ecr:BatchCheckLayerAvailability`, `ecr:BatchGetImage`, and `ecr:GetDownloadUrlForLayer` on the repository.
            </Warning>
          </Tab>
        </Tabs>
      </Step>
    </Steps>
  </Tab>
</Tabs>

## Bill of materials and uninstall

| Flow | What exists | What remains after uninstrumenting |
| --- | --- | --- |
| Odigos registry (default) | An image reference in the task definition | Nothing of yours. Old task-definition revisions still reference the image. |
| Private ECR mirror | The repository, the image index and layers, and optionally a repository policy and execution-role pull permissions | All of it, until you remove it. |
| CDK or CloudFormation `agentsImage` override | The mirror's image reference in your IaC and task definition | The reference stays until you change the IaC and deploy. |
| Odigos-managed controller override | `CONNECTOR_AWS_FARGATE_AGENTS_IMAGE` on `connector-runtime` | The variable stays, even if you delete one Source or connector, until you remove it. |

### Uninstall a mirror

1. [Uninstrument or redeploy](/cloud-connectors/aws/workloads/fargate/instrument#bill-of-materials-and-uninstall) every service that
   uses the mirror, or point it at an image that will stay available. Update scheduled and standalone tasks and
   deployment pipelines too.
2. Remove the `agentsImage` override from your IaC and deploy. If you set the controller override only for this mirror,
   restore its previous value, or remove it if there was none:

   ```bash
   kubectl set env deployment/connector-runtime -n odigos-central \
     CONNECTOR_AWS_FARGATE_AGENTS_IMAGE-
   ```

   This affects **all** AWS connectors on that controller. Keep the override while any of them still uses it, and check
   the resulting task definitions before you delete the image.
3. In ECR, delete the image with `aws ecr batch-delete-image` or the console. If the repository is shared, delete only
   this mirror's tag. If you created the repository only for this mirror and nothing else uses it, delete the repository
   instead (with ECR or the IaC that created it).
4. Remove the repository-policy statements and execution-role pull permissions you added for it, keeping any that other
   images need.

Running tasks keep the image they already downloaded, so a healthy task doesn't prove the cleanup is safe. A later
launch or scale-out fails if it still references the deleted image. Old task-definition revisions are separate; see
[Remove unused task-definition revisions](/cloud-connectors/aws/workloads/fargate/instrument#remove-unused-task-definition-revisions).
