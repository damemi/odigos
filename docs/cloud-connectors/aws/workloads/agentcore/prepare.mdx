AgentCore has no layers or sidecars, so the OpenTelemetry SDK has to travel inside your own artifact. The
recommended way is one dependency, the Odigos package: it brings the SDK and a small bootstrap that loads it
before your application code. You add it once, in the same build that produces your image or ZIP.
Instrumentation is then switched on by the runtime's environment variables, which the
[generated instructions](/cloud-connectors/aws/workloads/agentcore/instrument#self-managed-instrumentation) set.

<Note>
  Odigos-managed instrumentation uses the same package. It configures the SDK your artifact already carries (this
  package, a carrier bundle, or ADOT) and never rewrites the artifact, so only a runtime whose artifact carries
  none waits, until a deployment adds one. See [Odigos-managed instrumentation](/cloud-connectors/aws/workloads/agentcore/instrument#odigos-managed-instrumentation).
  Self-managed instrumentation has the same requirement.
</Note>

## Add the package

| Language | Package | Install |
| --- | --- | --- |
| Python | `odigos-agentcore` on PyPI | `pip install "odigos-agentcore[adot]"` or `pip install "odigos-agentcore[openllmetry]"` |
| Node.js / compiled TypeScript | `@odigos/agentcore` on npm | `npm install @odigos/agentcore` |

The Python extra selects the SDK the package installs next to it: `[adot]` for AWS Distro for OpenTelemetry,
`[openllmetry]` for OpenLLMetry. **The extra you choose must match the distribution selected in Odigos**
(`python-agentcore-adot` or `python-agentcore-openllmetry`). Installing the package without an extra leaves the
artifact with no SDK. The Node.js package carries both distributions, so the distribution is selected by the
runtime's environment alone.

Install it with your other dependencies, in the build that already produces your artifact, and pin the version
in your requirements file or lockfile. Dependency resolution happens in your own resolver, so your application
keeps the versions of shared libraries it pins.

The bootstrap is **dormant**. Until the runtime sets `ODIGOS_AGENTCORE_ENABLED=true`, it loads nothing and your
application runs exactly as before, so you can ship the prepared artifact ahead of turning instrumentation on.

<Tabs>
  <Tab title="Direct-code ZIP">
    Install the dependencies into the directory you ZIP and keep your entry point as it is. The package brings
    a start wrapper, which Odigos-managed instrumentation makes the entry point.

    <Steps>
      <Step title="Install the package into your build directory">
        <CodeGroup>
          ```bash Python
          pip install \
            --platform manylinux2014_aarch64 --python-version 3.12 --only-binary=:all: \
            --target build "odigos-agentcore[adot]"
          ```

          ```bash Node.js
          npm install @odigos/agentcore
          ```
        </CodeGroup>
        `build/` (or your Node.js project directory) is the directory you already ZIP, with your application and
        its dependencies at the root. The Python install puts `odigos_agentcore_start.py` at the ZIP root;
        for Node.js, `node_modules` must be in the ZIP.
      </Step>

      <Step title="ZIP and upload as usual">
        ```bash
        (cd build && zip -qr ../agent.zip .)
        aws s3 cp agent.zip s3://<bucket>/<key>
        ```
      </Step>

      <Step title="Leave the entry point to Odigos">
        Keep your entry point, for example `[app.py]` or `[index.js]`. With Odigos-managed instrumentation the
        connector makes the package's start wrapper the entry point, `[odigos_agentcore_start.py]` or
        `[node_modules/@odigos/agentcore/odigos_agentcore_start.js]`, and names your script in
        `ODIGOS_AGENTCORE_ENTRYPOINT`. AgentCore accepts a second entry point element only after its own
        `opentelemetry-instrument` prefix, so do not put the wrapper in front of your script yourself.

        The wrapper loads the bootstrap, then runs your entry point with the same working directory, arguments,
        exit status and signals. An `opentelemetry-instrument` prefix you already use is replaced by the wrapper,
        so the application does not run two SDKs. Disabling instrumentation restores your entry point.

        With self-managed instrumentation you set both yourself. Make the entry point the wrapper alone, for
        example `["odigos_agentcore_start.py"]` or `["node_modules/@odigos/agentcore/odigos_agentcore_start.js"]`,
        and set the runtime environment variable `ODIGOS_AGENTCORE_ENTRYPOINT=<your entry point>`, for example
        `ODIGOS_AGENTCORE_ENTRYPOINT=app.py`, relative to the ZIP root. The generated instructions carry both.
      </Step>
    </Steps>
  </Tab>

  <Tab title="Container image">
    Install the package in the image build. Both lines go in your existing Dockerfile.

    <CodeGroup>
      ```dockerfile Python
      RUN pip install "odigos-agentcore[adot]"
      ```

      ```dockerfile Node.js
      RUN npm install @odigos/agentcore
      ENV NODE_OPTIONS="--require @odigos/agentcore/register ${NODE_OPTIONS}"
      ```
    </CodeGroup>

    **Python needs nothing further.** The wheel installs an `odigos_agentcore.pth` file into `site-packages`,
    which imports the dormant bootstrap when the interpreter starts, so your `CMD` and `ENTRYPOINT` stay
    exactly as they are. Do not start the application through `opentelemetry-instrument` as well: that would
    run two SDKs.

    **Node.js adds the `--require`.** The loader appends to any value your image already sets. The bare
    specifier is resolved from the container's working directory, so `node_modules` must be installed there;
    otherwise use the absolute path to `node_modules/@odigos/agentcore/register.cjs`.

    Build for `linux/arm64`, push the image to the ECR repository your runtime uses, and point the runtime's
    `ContainerUri` at the new tag.

    <Warning>
      A `NODE_OPTIONS` set in the runtime's **EnvironmentVariables** replaces the image's value entirely. If
      your runtime sets it, add the `--require` entry there as well.
    </Warning>
  </Tab>
</Tabs>

## Alternative: copy the bundle from the image

If your build cannot install the package from PyPI or npm, copy the same bootstrap and both SDK
distributions from the carrier image instead. Everything below is the carrier image route; skip it if you
used the package.

### The bundle image

Odigos publishes the bundles as `registry.odigos.io/odigos-agentcore-agents:<version>`, a Linux arm64 image
(AgentCore microVMs are arm64). It contains no runtime of its own, only files:

| Path in the image | Contents |
| --- | --- |
| `/var/odigos/agentcore/python/3.12` | Python 3.12 bundle: the ADOT and OpenLLMetry distributions and `bootstrap/python` |
| `/var/odigos/agentcore/nodejs/22` | Node.js 22 bundle: the ADOT and OpenLLMetry distributions and `bootstrap/node` |

Each bundle carries both distributions, so switching between ADOT and OpenLLMetry later is an environment
change, not a rebuild. Use the exact `<version>` your generated instructions name: it is the release your
connector expects.

The bootstrap is dormant here too: it loads nothing until the runtime sets `ODIGOS_AGENTCORE_ENABLED=true`.

### Add the bundle

<Tabs>
  <Tab title="Container image">
    Copy the bundle to `/opt/odigos/agentcore` and add the loader. Both lines go in your existing Dockerfile,
    after the base image:

    <CodeGroup>
      ```dockerfile Python
      COPY --from=registry.odigos.io/odigos-agentcore-agents:<version> /var/odigos/agentcore/python/3.12 /opt/odigos/agentcore
      ENV PYTHONPATH=/opt/odigos/agentcore/bootstrap/python${PYTHONPATH:+:$PYTHONPATH}
      ```

      ```dockerfile Node.js
      COPY --from=registry.odigos.io/odigos-agentcore-agents:<version> /var/odigos/agentcore/nodejs/22 /opt/odigos/agentcore
      ENV NODE_OPTIONS="--require /opt/odigos/agentcore/bootstrap/node/register.cjs ${NODE_OPTIONS}"
      ```
    </CodeGroup>

    The loader appends to any value your image already sets. Build for `linux/arm64`, push the image to the
    ECR repository your runtime uses, and point the runtime's `ContainerUri` at the new tag.

    <Warning>
      A `PYTHONPATH` or `NODE_OPTIONS` set in the runtime's **EnvironmentVariables** replaces the image's value
      entirely. If your runtime sets either one, add the bootstrap entry there as well.
    </Warning>
  </Tab>

  <Tab title="Direct-code ZIP">
    Add the bundle to your ZIP as `odigos-agentcore/` and copy the start wrapper to the ZIP root. Keep your entry
    point as it is.

    <Steps>
      <Step title="Extract the bundle into your build directory">
        <CodeGroup>
          ```bash Python
          id=$(docker create --platform linux/arm64 registry.odigos.io/odigos-agentcore-agents:<version> odigos)
          docker cp "$id:/var/odigos/agentcore/python/3.12/." build/odigos-agentcore
          docker rm "$id"
          cp build/odigos-agentcore/bootstrap/python/odigos_agentcore_start.py build/
          ```

          ```bash Node.js
          id=$(docker create --platform linux/arm64 registry.odigos.io/odigos-agentcore-agents:<version> odigos)
          docker cp "$id:/var/odigos/agentcore/nodejs/22/." build/odigos-agentcore
          docker rm "$id"
          cp build/odigos-agentcore/bootstrap/node/odigos_agentcore_start.js build/
          ```
        </CodeGroup>
        `build/` is the directory you already ZIP, with your application and its dependencies at the root.
      </Step>

      <Step title="ZIP and upload as usual">
        ```bash
        (cd build && zip -qr ../agent.zip .)
        aws s3 cp agent.zip s3://<bucket>/<key>
        ```
      </Step>

      <Step title="Leave the entry point to Odigos">
        Keep your entry point. With Odigos-managed instrumentation the connector makes the wrapper the entry point,
        `[odigos_agentcore_start.py]` or `[odigos_agentcore_start.js]`, and names your script in
        `ODIGOS_AGENTCORE_ENTRYPOINT`. AgentCore accepts a second entry point element only after its own
        `opentelemetry-instrument` prefix, so do not put the wrapper in front of your script yourself.

        With self-managed instrumentation you set both yourself. Make the entry point the wrapper alone,
        `["odigos_agentcore_start.py"]` or `["odigos_agentcore_start.js"]`, and set the runtime environment
        variable `ODIGOS_AGENTCORE_ENTRYPOINT=<your entry point>` to your script, relative to the ZIP root.
        The generated instructions carry both.
      </Step>
    </Steps>

    The bundle adds roughly 30 to 45 MB compressed. Direct code is limited to 250 MB compressed; use a container
    for larger applications.
  </Tab>
</Tabs>

### Use a private registry

The image is needed only for this route, so `registry.odigos.io` must be reachable only from the build that
copies the bundle. If your build cannot reach it, or your organization requires images from registries you own,
mirror the image first and copy from the mirror:

```bash
aws ecr create-repository --repository-name odigos-agentcore-agents --region <region>
aws ecr get-login-password --region <region> \
  | docker login --username AWS --password-stdin <account-id>.dkr.ecr.<region>.amazonaws.com
docker buildx imagetools create \
  --tag <account-id>.dkr.ecr.<region>.amazonaws.com/odigos-agentcore-agents:<version> \
  registry.odigos.io/odigos-agentcore-agents:<version>
```

The bundle is only read at build time, so the runtime itself never pulls from either registry. The package
route needs no Odigos registry at all, only the package registry your build already uses.

## Requirements and limits

- **Python 3.12 and Node.js 22, Linux arm64.** Node.js applications must be CommonJS (TypeScript compiled to
  CommonJS). Native ESM is not supported by the bootstrap.
- **One `sitecustomize` for ZIPs and the bundle image route.** Python imports only the first `sitecustomize.py`
  on its path, and the ZIP start wrapper and the copied bundle load the bootstrap through one of their own. The
  package's container route starts through a `.pth` file instead and coexists with your `sitecustomize.py`.
- **One SDK.** Remove any OpenTelemetry setup the application already does (an `opentelemetry-instrument`
  launcher, a `--require` of an OTel register, or code that creates a tracer provider).
- **Match the extra to the distribution.** For Python, the `odigos-agentcore` extra you install must be the one
  for the distribution selected in Odigos (`[adot]` for `python-agentcore-adot`, `[openllmetry]` for
  `python-agentcore-openllmetry`). If you change the distribution later, change the extra in your build.
- **Pinned versions.** Keep the package version (or the carrier `<version>`) pinned in your build. A newer
  release is picked up by rebuilding, which is a release you control.
