The Odigos AWS CDK package adds OpenTelemetry instrumentation to your AWS workloads from inside your own
[AWS CDK](https://aws.amazon.com/cdk/) application — so instrumentation ships through the same pipeline as
the rest of your infrastructure, reviewed in a pull request and applied by `cdk deploy`.

<Info>
  **New to this?** AWS CDK is a tool for describing cloud infrastructure in a
  programming language instead of a YAML template. If your team doesn't use CDK,
  you don't need this section — use the CloudFormation instructions on
  [Instrument Lambda](/cloud-connectors/aws/workloads/lambda/instrument) or
  [Instrument Fargate](/cloud-connectors/aws/workloads/fargate/instrument), or let
  Odigos apply instrumentation for you.
</Info>

## When you'd use this

Odigos can instrument your workloads two ways, and the CDK package is for the second one:

| | Odigos-managed | Self-managed, with this package |
| --- | --- | --- |
| Who changes the workload | Odigos, automatically | Your CDK app, on `cdk deploy` |
| Where instrumentation is defined | In Odigos | In your own source code |
| What Odigos does | Applies and maintains it | Watches and reports |

Pick self-managed when your infrastructure code should stay the single source of truth for what's deployed.
Pick Odigos-managed when you'd rather not touch your infrastructure code at all. Full comparison:
[Odigos-managed vs. self-managed instrumentation](/cloud-connectors/overview#odigos-managed-vs-self-managed-instrumentation).

<Warning>
  Don't do both to the same workload. If a function or service is instrumented by
  your CDK app **and** also enabled as an Odigos-managed source, each side keeps
  reasserting its own configuration — every deploy fights every reconcile, and each
  round trip rewrites the Lambda function's configuration or registers a new ECS task
  definition revision. Pick one per workload.
</Warning>

## Install

```bash
npm install --save-exact @odigos/aws-cdk@0.0.27
```

The package needs `aws-cdk-lib` `^2.150.0`, `constructs` `^10.0.5`, and Node.js 18.12 or later.

<Info>
  **TypeScript and JavaScript only, for now.** A Python distribution
  (`odigos-aws-cdk`) is built but not yet published. Until it's out, Python CDK apps should use the
  [CloudFormation instructions](/cloud-connectors/aws/workloads/lambda/instrument#using-cloudformation-directly)
  instead.
</Info>

**The package version *is* the instrumentation version.** `@odigos/aws-cdk@0.0.27` uses the OpenTelemetry layers and
agents bundle built by Odigos release `v0.0.27`, and nothing resolves or moves at deploy time. Upgrading is a
deliberate `npm update` followed by a `cdk diff` that shows exactly what changes.

## The two constructs

| | Lambda | ECS Fargate |
| --- | --- | --- |
| Construct | `OdigosLambdaInstrumentation` | `OdigosFargateInstrumentation` |
| How the agent gets there | A Lambda layer attached to the function | Copied into the task by an extra short-lived container |
| Languages | Java, Python, Node.js, Ruby — with a [choice of distro](/cloud-connectors/aws/workloads/lambda/distros) per language | Java, Python, Node.js, .NET, PHP, Ruby — one agent per language |
| Where telemetry goes | To a collector inside the same Lambda sandbox, which forwards it on after your handler returns | Straight from your application to your destination |
| How the language is determined | Automatically, from the function's runtime | You state it explicitly |

## How Odigos recognizes your workload

Both constructs mark everything they instrument, so Odigos can tell "this workload is instrumented, and here's
what with." The marker differs by service:

| | Lambda | ECS Fargate |
| --- | --- | --- |
| Where the marker lives | Function **tags** | The **`ODIGOS_IAC`** environment variable on the container |
| What it records | `odigos:iac=v1`, `odigos:sdk-layer` (the exact SDK layer ARN), and `odigos:collector-layer` (ADOT only) | The package version, the language, and the agents image |

<Warning>
  Without that marker, Odigos reports the workload as **Waiting for you to apply the instrumentation** —
  no matter how completely everything else was applied. The constructs write it for
  you, so there's nothing to switch on; it matters mainly because you'll see it in
  a `cdk diff`, and because hand-written instrumentation has to include it too.
</Warning>

The marker also records *which version* of instrumentation you deployed — the layer ARNs on Lambda, the
agents image on Fargate. That's what lets you pin a version and have Odigos respect it, rather than
reporting your deliberately-pinned workload as out of date the day Odigos publishes something newer.

### Lambda: tags

The Lambda construct adds the tags with `Tags.of(fn)`. CDK applies a tag to every taggable resource under the
function, so the function's **auto-created execution role is tagged too**. That's normal CDK behavior, not
something to fix.

The construct also removes any `ODIGOS_IAC` or `ODIGOS_MANAGED` environment variables from the function's
definition, such as ones written by an earlier package version. The only environment variables it writes are
`AWS_LAMBDA_EXEC_WRAPPER` and `ODIGOS_LAMBDA_CONFIG`, plus your loader variable when you pass `existingLoaderValue`. See [CDK: Lambda](/cloud-connectors/aws/cdk/lambda).

<Note>
  The deploying identity needs `lambda:TagResource` for the tags to be applied. A function
  with no `odigos:iac` tag is treated as not instrumented.
</Note>

### Fargate: the `ODIGOS_IAC` variable

Fargate still uses the environment variable, with this shape:

```json
{"v":1,"source":"cdk","version":"v0.0.27","lang":"java","image":"registry.odigos.io/odigos-fargate-agents:v0.0.27"}
```

Odigos reads `lang` and `image`; `v`, `source`, and `version` are informational.

<Warning>
  There's a second marker, **`ODIGOS_MANAGED`**, that these constructs never write —
  and neither should you. That one is Odigos' own record of a change *it* made,
  including the snapshot it would undo that change with. Writing it by hand claims a
  rollback point that doesn't exist.
</Warning>

## Turning on debug logging

<ParamField path="debug" type="boolean" default="false">
  Makes the OpenTelemetry agent log verbosely, which helps when telemetry isn't arriving and you need to
  see why. Available on both constructs. On Lambda it sets `"debug": true` in `ODIGOS_LAMBDA_CONFIG` (and has no
  effect for functions in web-server mode); on Fargate it sets `OTEL_LOG_LEVEL=debug` on every instrumented
  container.

  <Warning>
    Leave it off once you're done. It's expensive at volume, and Odigos expects it
    **off** unless debug telemetry is also enabled on the connector — so leaving it
    on can itself be reported as drift.
  </Warning>
</ParamField>

## Bill of materials and uninstall

| Stage | What exists | Removal |
| --- | --- | --- |
| `npm install @odigos/aws-cdk` | A dependency and lockfile entry | Remove after the workloads are rolled back |
| Synth and deploy | Changes to existing Lambda functions and task definitions, plus optional SAR layer stacks and role-policy attachments | See the [Lambda](/cloud-connectors/aws/cdk/lambda#bill-of-materials-and-uninstall) and [Fargate](/cloud-connectors/aws/cdk/fargate#bill-of-materials-and-uninstall) inventories |
| CDK bootstrap | The shared `CDKToolkit` stack, its asset bucket and ECR repository, and `cdk.out` | Keep these. They're shared with the rest of your CDK apps. |

1. Disable the affected self-managed Sources. Remove the instrumentation calls and aspects from your CDK app, restore the original properties, review `cdk diff`, and deploy. Removing the npm package alone doesn't change AWS.
2. Verify the clean Lambda versions and aliases and the Fargate rollouts, then clean up retained layers, old task revisions, and private mirrors using the guides linked above.
3. Once no code imports the package, remove it:

   ```bash
   npm uninstall @odigos/aws-cdk
   ```

4. Remove leftover imports and configuration. Generated templates, lockfiles, and backups can retain copies of destination headers. Don't run `cdk destroy` on the application stack or delete `CDKToolkit` to remove instrumentation.

The application and your shared deployment infrastructure stay. For retained artifacts and external resources, see the [AWS uninstall inventory](/cloud-connectors/aws/uninstall).
