# AGENTS.md - Odigos Insights

- Every feature must account for **HA**: insights runs as **multiple replicas** sharing one ClickHouse. Per-pod state (baselines, policy snapshots, buffers) can lag; durable state in ClickHouse is the source of truth.
- The **interrogation** feature (`internal/interrogation`, enabled via `INTERROGATION_ENABLED`) is the exception: its loop writes InstrumentationRules and must be single-writer, so it runs only on the replica holding the `odigos-insights-leader` lease (the same lease singleton insights jobs use). Call tries and analysis runs live in the `interrogation` ClickHouse database. Transaction inventory is the shared insights `transactions` table, which also carries a `source_identity` map so sources are not schematically bound to Kubernetes. `transaction_id` hashes the source identity, so each workload has its own transactions, and trie transaction ids are hashed with the engine's same `SourceIdentityFunc`. The loop discovers sources and their transactions from `tx_call_trie_structure` (semi-joined to `transactions` for operation/kind), never from `source_identity`. Tries are recorded only for identities the per-service cap admitted, so every trie has an inventory row. It must never block ingest or `/readyz`. Its invariants and open follow-ups are in `internal/interrogation/AGENTS.md`.
- **No database reads or writes on the trace hot path** (`Engine.Process` / `processOne`). Persistence goes through in-memory stores and write-behind flush.
- **Never rely on reload timing for correctness.** A snapshot can be up to a reload interval stale on any replica. If stale state would produce a wrong result (a false finding, an overwritten value), make the state **self-describing** so the holder can reject it locally.
- **Fingerprint stamping** is the pattern for that: store, next to the data, a hash of the config it was derived under (`repo.IdentityDimensionsFingerprint` → `ServiceGuardrail.RuleFingerprints`). A replica compares the stamp to the config it is actually using and skips the rule on mismatch - no coordination, no lag.
- **Epoch tagging** keeps a buffered write from outliving the data it describes. Deleting all transactions bumps `transaction_inventory_epoch`; each buffered violation count carries the epoch its replica believed while counting, and the flush drops counts whose epoch has moved on (`guardrailBuffer.drain`). Without it, a replica that never noticed the delete flushes counts for transactions that no longer exist, re-creating the findings the delete just cleared. Re-read the counter **from storage** on the flush path, never from the local snapshot - the local snapshot is the thing that may be stale.
