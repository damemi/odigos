Learning examples

While learning, collect up to example traces per transaction, at most one every seconds, then stop. Anomaly and guardrail evidence each keep a single write-once sample; occurrences are counted separately.

Retention

Delete stored sample traces after days (default 120, max 120; applied on save). Matches the findings lookback ceiling.

Memory limits

Caps how much baseline state the engine keeps in RAM. Higher = more coverage, more memory.

Keep baselines for at most transactions in memory. When the limit is hit, the least-recently used ones are dropped (they re-load later if traffic returns).

Per baseline set (e.g. unique call edges or paths for one class), remember at most members so a noisy transaction cannot grow unbounded.

Database writeback

How often pending learning and occurrence counts are written to ClickHouse. Raise this under DB load; lower it when you want fresher counts. Applies live — no restart.

Flush every seconds (default 15, max 300).

Transaction guardrails

When a service finishes promoting (every transaction leaves learning), automatically create an enforced allowed_transactions guardrail. Applies only from that moment forward — services already promoted are not backfilled; enable their guardrail from the by-service transactions menu. Per-service disable uses rule mode off.

Transaction identity dimensions

Low-cardinality only. Each enabled dimension multiplies transaction count, resident memory, and baseline rows. Good: http.response.status_code, rpc.grpc.status_code. Bad: user.id, URLs, request ids, emails. Values come from the entry span only. Changing dimensions creates new transaction identities; you will be asked whether to reset existing ones.
