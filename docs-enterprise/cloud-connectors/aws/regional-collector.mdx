The **regional Collector** is an Odigos OpenTelemetry Collector that runs in **your** AWS account, with at
most one per region. It runs as an ECS Fargate service behind an **internal** Network Load Balancer (NLB),
and Odigos manages its configuration over OpAMP, so you never edit a Collector config file.

Instrumented workloads in the same region export to the Collector inside your VPC instead of each sending
directly to the backend. That gives you:

- **A short, in-VPC hop.** Workloads export to a regional endpoint, not to the backend across the network.
- **One place for backend credentials.** The Collector holds the credentials for its downstream destinations,
  so workloads don't need them.
- **A central place for routing.** You choose where a region's telemetry goes from the Collectors page in
  Central, without touching the workloads.

<Info>
  The regional Collector is an AWS Connector capability. It is off by default, and your Odigos Central
  installation must enable managed Collectors first. See
  [Prerequisites](#prerequisites).
</Info>

## Which workloads use it

A workload exports through the regional Collector when it is in the same region as the Collector and can
reach it over the network:

| Workload | Uses the Collector? |
| --- | --- |
| Fargate service | Yes, when it can reach the Collector. |
| Lambda function attached to a VPC | Yes, when it can reach the Collector. |
| Lambda function **not** attached to a VPC | Never. It always exports directly to your global destination. Odigos never attaches a function to a VPC or changes its `VpcConfig`. |

A workload can reach the Collector when **all** of the following hold:

- **Network path.** It runs in the **same VPC** as the Collector, or the two VPCs have an **active,
  same-region VPC peering connection** with non-overlapping CIDR blocks and a route to the other VPC in every
  workload and Collector subnet.
- **DNS.** DNS support is enabled on both VPCs.
- **Security groups.** The workload's security groups allow outbound traffic to the Collector. The Collector's
  security group admits the workload's security group, or every workload subnet CIDR, on TCP **4317** (OTLP
  gRPC) and **4318** (OTLP HTTP). The Collector's security group also admits **itself** on those ports,
  because traffic from the load balancer to the tasks needs it, and on TCP **13133** for health checks.
- **Network ACLs.** For each OTLP port the Collector publishes, the workload and Collector subnet ACLs allow
  the request in both directions, and allow TCP return traffic on ports 1024-65535. ACL rules are read in
  number order. An earlier deny wins, and a rule that allows only part of a range doesn't count.

Odigos reads these settings from AWS before it routes a workload. It keeps the workload on direct export when
a check fails or can't be answered.

<Warning>
  Odigos does not create VPC peering, routes, or network ACL rules. If a workload runs in a different VPC, set
  up the peering and routes yourself. See [Routing notes](#routing-notes) for the message a workload shows
  while it can't reach the Collector.
</Warning>

## Prerequisites

<Steps>
  <Step title="Enable managed Collectors in Central">
    The Odigos Central Helm chart must have cloud connectors and managed Collectors enabled, with an external
    OpAMP endpoint that Collectors running in AWS can reach. See
    [Managed Collectors](/cloud-connectors/enable#managed-collectors).
  </Step>
  <Step title="An ACTIVE ECS cluster">
    The Collector runs as a service in an ECS cluster you already have. The cluster only needs to be
    `ACTIVE`; it doesn't need other services or EC2 capacity. Odigos never creates a cluster.
  </Step>
  <Step title="A VPC with outbound access">
    The Collector's tasks need egress to pull the image, read Secrets Manager, reach Odigos Central over
    OpAMP, and reach the Collector's downstream destinations. That means a NAT gateway or other central
    egress route for private subnets, or an internet gateway route for public subnets, depending on the
    [outbound path](#install-a-collector-automatic) you choose.
  </Step>
  <Step title="An ECS task execution role">
    The role that ECS uses to start the Collector tasks. **You create it, once per connector in each AWS
    account.** Odigos never creates IAM roles. The install wizard gives you a CloudFormation template and
    AWS CLI commands for it. See step 1 of [Install a Collector (automatic)](#install-a-collector-automatic).
  </Step>
  <Step title="IAM permissions on the connector identity">
    The connector uses the credentials you already gave it; there is no separate role for the Collector.
    Select the Collector access level when you add the connector and the permission preview shows exactly
    what the connector needs. See
    [IAM permissions](/cloud-connectors/add-connectors/add-aws-connector#iam-permissions).

    Both modes need read access to the region's network, including `ec2:DescribeNetworkAcls` and
    `ec2:DescribeVpcAttribute`. Without them Odigos can't scan the region's network.

    In automatic mode, the connector's policy also needs `iam:PassRole` for the **ARN of your Collector
    execution role** (in addition to the `iam:PassRole` that Fargate instrumentation uses), with the condition
    `iam:PassedToService` equal to `ecs-tasks.amazonaws.com`.

    <Warning>
      Never grant `iam:CreateRole`, `iam:PutRolePolicy`, `iam:TagRole`, or `iam:DeleteRole` to the connector.
      It doesn't need them.
    </Warning>
  </Step>
</Steps>

<Note>
  The connection test doesn't check Collector permissions. A connector can pass the test and still fail to
  install or manage a Collector if the permissions for your chosen mode are missing.
</Note>

## Modes

The Collector mode is set **per connector**.

| Mode | What you do | What Odigos does | What Odigos never does |
| --- | --- | --- | --- |
| **Off** | Nothing. | Nothing. Workloads export directly. If a Collector already exists, Odigos revokes its credentials and it keeps running on its last configuration. | Create, read, or delete Collector infrastructure. |
| **Manual (customer IaC)** | Deploy the Collector yourself from generated IaC. | Finds the Collector by its tags, observes it, pushes its configuration (destinations and actions) over OpAMP, and routes workloads to it once it is ready. | Create, repair, or delete any of your infrastructure. |
| **Automatic** | Create the execution role once, then run the install wizard. | Everything in Manual, plus creates and keeps in sync the ECS service, task definition, internal NLB, listeners, target groups, security group, log group, Secrets Manager secrets (the OpAMP credential, the license, and, when needed, a startup configuration), and autoscaling when it is enabled. | Create your ECS cluster, VPC, or execution role. |

Both modes need an `ACTIVE` ECS cluster and an ECS task execution role that you provide.

### Choose a mode when you create the connector

In the access level step of the connector wizard:

- Select **Discovery + instrumentation + collector** for **Automatic**.
- Select **Custom** and use the **Collector** section for finer control. The **Management** and
  **Installation** toggles map to the modes: Management alone is Manual, Management plus Installation is
  Automatic.

### Change the mode later

<Steps>
  <Step title="Open the row action">
    On the **Connections** page, open the action menu on the connector's row and choose **Collector mode**.
  </Step>
  <Step title="Pick a mode">
    In the **Regional Collector mode** drawer, choose **Off**, **Manual (customer IaC)**, or **Automatic**.
  </Step>
  <Step title="Save">
    Click **Save and restart connector**.
  </Step>
</Steps>

<Warning>
  Changing the mode **restarts the connector**. Only Central administrators can change it.
</Warning>

## Install a Collector (automatic)

In automatic mode, Odigos deploys the Collector for you. Select the connector on **Connections**, then open
**Collectors** in the left navigation. The page is titled **Managed Collectors**. Click **Install new
collector** (or **Install collector** from an empty state) to open the install wizard.

The wizard has three phases, **Prepare**, **Configure**, and **Verify**, across nine steps. At the top, a
method switch lets you view each step as an **Overview**, as **AWS CLI** commands, or as a
**CloudFormation** template.

<Steps>
  <Step title="Pre-create the Collector task execution role">
    The wizard gives you a CloudFormation template and an AWS CLI script for the execution role. Deploy the
    template, then paste the role ARN from the stack output **`ExecutionRoleArn`**. With the CLI script, the
    role is named `odigos-collector-<connector>-execution`.

    <img
      src="/images/cloud-connectors/aws-collector-execution-role.png"
      alt="Install collector wizard, step 1, showing the execution role CloudFormation template and the Execution role ARN field"
    />

    - Set the **`ConnectorName`** parameter to the **exact name of this connector**. The permissions in the
      role are scoped by that name.
    - Deploy the stack **once per connector in each AWS account**. IAM roles are account-wide, so a role you
      already created for one region works for the others.
    - Only `ecs-tasks.amazonaws.com` in your account can assume the role. It can write to the log group
      `/odigos/collector/<connector>` and read the secrets under `odigos/collector/<connector>/`, and nothing
      else.
    - If you pull the Collector image from a **private ECR** repository, the role also needs
      `ecr:GetAuthorizationToken`, `ecr:BatchCheckLayerAvailability`, `ecr:BatchGetImage`, and
      `ecr:GetDownloadUrlForLayer` on that repository.
    - If your secrets are encrypted with a **customer-managed KMS key**, the role also needs `kms:Decrypt`
      on that key.

    Remember to allow the connector's `iam:PassRole` for this role's ARN (automatic mode). See
    [Prerequisites](#prerequisites).
  </Step>
  <Step title="Select the Collector region">
    Choose the region for this Collector. There is at most one Collector per region, and only workloads in
    that region use it.
  </Step>
  <Step title="Choose the ECS cluster">
    Enter the ARN of an existing `ACTIVE` ECS cluster. Odigos does not create the cluster, and the cluster
    needs no other services or EC2 instances.
  </Step>
  <Step title="Choose the VPC">
    Enter the VPC ID. Odigos picks the subnets itself: subnets with free IP addresses and a usable outbound
    route, preferably spread over at least two Availability Zones. You can see the choice later on the Collector's
    overview.
  </Step>
  <Step title="Choose the outbound path">
    This controls how the Collector tasks reach the internet: for image registries, Secrets Manager, the
    Odigos OpAMP endpoint, and the Collector's downstream destinations.

    | Option | Task public IP | Your VPC needs |
    | --- | --- | --- |
    | **Private** | No | A default route to a NAT gateway or central egress. |
    | **Public** | Yes | A route to an internet gateway. |

    The Collector's load balancer is **internal** either way. Workloads never reach it from the internet.
  </Step>
  <Step title="Choose the Collector size">
    Each task gets a fixed amount of CPU and memory. **Medium** is the default.

    | Size | vCPU | Memory |
    | --- | --- | --- |
    | Small | 0.5 | 1 GiB |
    | **Medium** (default) | 1 | 2 GiB |
    | Large | 4 | 8 GiB |
    | X-Large | 8 | 16 GiB |
    | 2X-Large | 16 | 32 GiB |
    | 3X-Large | 32 | 60 GiB |

    <img
      src="/images/cloud-connectors/aws-collector-size.png"
      alt="Install collector wizard showing the Collector size options from Small to 2X-Large"
    />

    By default the service runs a fixed **2 tasks** and keeps Collector logs for **7 days**. With automatic
    scaling (`scaling.mode: auto`) it runs 2 to 10 tasks, targeting 70% CPU and 75% memory.
  </Step>
  <Step title="Prepare automatic scaling">
    ECS autoscaling needs the Application Auto Scaling service-linked role for ECS. The wizard shows the
    command that creates it if your account doesn't have it yet:

    ```bash
    aws iam create-service-linked-role \
      --aws-service-name ecs.application-autoscaling.amazonaws.com
    ```

    You only need this role if the Collector uses automatic scaling. By default it runs a fixed number of
    tasks, so you can skip the command.
  </Step>
  <Step title="Review and install">
    Review the summary, then click **Install Collector**. This is the step that creates resources in your
    AWS account.

    <img
      src="/images/cloud-connectors/aws-collector-review.png"
      alt="Install collector wizard review step summarizing the execution role, region, cluster, VPC, outbound path, and size, with the Install Collector button"
    />
  </Step>
  <Step title="Verify">
    Odigos shows the Collector's progress until it reports **Healthy**. See
    [Collector status](#collector-status).
  </Step>
</Steps>

<Info>
  Odigos creates a security group for the Collector and keeps its inbound rules in sync. It admits OTLP
  traffic (TCP 4317 and 4318) from the security groups of the enabled Fargate services and VPC-attached Lambda
  functions that route to the Collector, and the group admits itself on 4317, 4318, and 13133. Rules that
  aren't in that set are removed, including rules you add by hand. If no workload is routed yet, the Collector
  deploys without OTLP ingress and rules appear once workloads are instrumented.

  If Odigos can't resolve any workload security group for three discovery cycles, it falls back to admitting
  the Collector VPC's own CIDR blocks (by default never wider than /16), and reports the Collector as **Degraded** until a
  security group resolves.

  When Odigos picks the subnets, it prefers subnets with private egress, at most one per Availability Zone,
  across up to three zones. If only one zone is usable, the Collector runs with reduced availability.
</Info>

## Install a Collector (manual)

In manual mode you deploy the Collector with your own infrastructure-as-code. Odigos renders the IaC, issues
the credential the Collector uses to connect to Central, and takes over configuration once the Collector
connects. It never creates, repairs, or deletes your resources.

<Steps>
  <Step title="Open the install wizard">
    On **Collectors**, click **Install new collector** (or **Install collector** from an empty state).
    Choose the region, ECS cluster, and VPC as in the
    automatic flow, and pre-create the [execution role](#install-a-collector-automatic).
  </Step>
  <Step title="Enter your subnets and security group">
    Fill in **Collector subnet IDs** and **Collector security group ID**. Create the security group and the
    CloudWatch log group (`/odigos/collector/<connector>`) yourself first. The wizard's AWS CLI script and
    CloudFormation template (`odigos-collector-<connector>-prerequisites` stack) create both, with 30-day log
    retention.

    <Warning>
      The Collector security group must allow inbound **TCP 4317, 4318, and 13133 from the group itself**.
      The generated prerequisites include those rules. Add the workload rules yourself when you route
      telemetry: allow TCP 4317 and 4318 from each workload's security group. The deployment instructions
      include the `aws ec2 authorize-security-group-ingress` commands. Until you add them, workloads keep
      exporting directly. If you supply an existing group, check all of these rules.
    </Warning>
  </Step>
  <Step title="Save the Collector configuration">
    Click **Save Collector configuration**. This only records your choices in Odigos. **It creates nothing in
    AWS.**
  </Step>
  <Step title="Create the credential secret">
    Create an empty Secrets Manager secret named `odigos/collector/<connector>/<region>/credential`. Then
    click **Issue credential** and put the value in the secret.

    <Warning>
      The credential is shown **once**. Copy the complete header and store it in the AWS secret before you
      deploy the ECS service. It can't be retrieved after the wizard closes. Issuing a credential needs the
      Central owner or admin role.
    </Warning>
  </Step>
  <Step title="Create the license secret">
    Create a second secret named `odigos/collector/<connector>/<region>/license` with this value, using your
    on-prem token:

    ```json
    {"username":"odigos","password":"<ON_PREM_TOKEN>"}
    ```
  </Step>
  <Step title="Deploy">
    In **Deploy method**, choose **CloudFormation**, **AWS CLI**, or **Terraform**. The wizard renders the
    document with your values. Fill in the remaining placeholders it lists under **Fill these in before
    applying**. You can open the same documents later from **Download config** on the Collectors page.

    The document creates the task definition, the ECS service, the internal NLB, its two target groups, and
    its two listeners (plus an autoscaling target and two scaling policies if scaling is automatic). The
    CloudFormation stack is named `odigos-collector-<connector>-<region>`. Apply the document with your own
    IaC principal, not the connector's.
  </Step>
  <Step title="Verify">
    Wait for the Collector to connect and report **Healthy**. See [Collector status](#collector-status).
  </Step>
</Steps>

Tag the resources you create so Odigos can find them:

| Tag | Value |
| --- | --- |
| `odigos-component` | `collector` |
| `odigos-connector` | The connector name |
| `odigos-connector-id` | The connector ID |
| `odigos-region` | The Collector's region |
| `odigos-network` | The ID of the VPC the Collector runs in |
| `odigos-iac` | `customer` |

The rendered IaC includes these tags, so keep them as generated.

## Route workloads to the Collector

Creating a Collector doesn't move any traffic. Workloads switch over when you add a routing destination.

<Steps>
  <Step title="Add the destination">
    On the connector, add a destination of type **Odigos Managed Regional Collector** and choose the
    **Region**. The type is only offered once the Collector capability is on and a Collector in a region has
    an endpoint.

    <Tip>
      Keep a **global OTLP destination** (OTLP gRPC or OTLP http) configured as well. Workloads that can't
      reach the Collector fall back to it, including non-VPC Lambda functions and workloads in other
      networks. This is recommended.
    </Tip>
  </Step>
  <Step title="Wait for the Collector to be ready">
    Odigos only routes to a Collector after it has reported ready at least once. After that, the decision is
    remembered, so a later blip in readiness doesn't send everything back to direct export. Odigos
    re-evaluates routing immediately when destinations or sources change or when a Collector becomes ready,
    without waiting for the next discovery interval.
  </Step>
  <Step title="Workloads cut over">
    Eligible workloads are updated to export through the Collector. How that happens depends on whether you
    have a global destination.
  </Step>
</Steps>

A workload goes through the Collector only when **all** of these are true:

- A routing destination exists for the Collector's region.
- The Collector has an endpoint.
- The Collector has reported ready at least once.
- The workload can [reach the Collector](#which-workloads-use-it).

### Cutover behavior

<Tabs>
  <Tab title="With a global destination">
    The cutover is gradual, so one bad rollout doesn't hit everything at once.

    - Once the Collector is ready and there are eligible instrumented workloads, Odigos announces a
      **one-minute warning window**. Nothing moves until it ends.
    - Workloads then move in **batches of up to 10** per pass by default, shared between Fargate services
      and Lambda functions.
    - Each moved workload gets a **new revision**: a new task definition revision for a Fargate service, or an
      updated configuration for a Lambda function.
    - Failed cutovers are retried, oldest first. At most half of each batch is retries, so workloads that
      haven't been tried yet are never starved.

    Workloads waiting for their turn keep using the global destination.
  </Tab>
  <Tab title="Without a global destination">
    There is nothing to fall back to, so there is no gradual cutover. Workloads route to the Collector
    **immediately** after it first reports ready.
  </Tab>
</Tabs>

To stop using the Collector, **disable** the routing destination. All workloads return to direct export.

### Where the Collector sends data

The routing destination only chooses the path *to* the Collector. Where the Collector sends telemetry next
is configured separately, per region, on the Collectors page.

<Steps>
  <Step title="Open the Collector">
    On **Collectors**, select the region.
  </Step>
  <Step title="Add a downstream destination">
    In the **Destinations** card, click **Add destination** and choose the backend. Select the signals it
    receives: traces, metrics, logs, or any combination, with at least one. The table shows each
    destination's type, name, signals, and status.
  </Step>
</Steps>

<Warning>
  A Collector with **no downstream destination accepts telemetry and discards it.** Add at least one before
  routing workloads to it. Profiles aren't accepted by the Collector.
</Warning>

## Collector actions

Actions are processing steps that a region's Collector applies to telemetry before it sends it to **every**
destination of that Collector. Each action belongs to one regional Collector, and removing the Collector
deletes its actions.

Actions only affect telemetry routed **through** the Collector. Workloads that export directly, such as
non-VPC Lambda functions, workloads that can't reach the Collector, or workloads still waiting for cutover,
bypass them.

### Add an action

<Steps>
  <Step title="Open the Actions tab">
    On **Collectors**, select the region. On the overview, switch from **Destinations** to **Actions**.
    With no actions, the card shows **No actions** and "Add an action to configure this collector."
  </Step>
  <Step title="Add an action">
    Click **Add action**. Pick an action type, using the categories (**All Actions**, **Enrichment**,
    **Normalization**, **Privacy & Governance**) or the **Search by action name** box.
  </Step>
  <Step title="Configure and save">
    Fill in the fields for the type and save. The region is preset and can't be changed. The table shows each
    action's name, type, signals, and status (**Active** or **Disabled**).
  </Step>
</Steps>

To change or remove an action, click **Edit** on its row. You can delete it from the drawer that opens.

<Note>
  Actions and destinations are Collector configuration, which Odigos pushes over OpAMP in both modes. You can
  add and edit them in **Manual** and **Automatic** mode alike.
</Note>

<Note>
  Collector actions require Odigos **v1.39 or later**: Central, the connector, and the Collector image.
</Note>

### Action types

| Action | Signals | What it does | Key fields |
| --- | --- | --- | --- |
| **URL Templatization** | Traces | Creates stable routes from HTTP URLs. | **Rule groups**, each with **Templates** such as `/users/{id}`. At least one template is required. |
| **Processor Addition** | Depends on the processor | Adds an OpenTelemetry processor to the pipeline. | **Processor type** (default `attributes`), **Processor name**, **Processor configuration (JSON)**. |
| **Span Metrics** | Traces in, metrics out | Generates metrics from spans. | All optional: **Interval**, **Metrics expiration**, **Additional dimensions**, **Disable latency histogram**, **Explicit histogram buckets**, **Resource metric key attributes**, **Include process in dimensions**, **Excluded resource attributes**, **Disable span metrics**. |
| **DB Query Templatization** | Traces | Replaces literals in database queries with placeholders. | **Templatize literals** (on by default), **Remove PostgreSQL cast operator**. At least one must be on. |
| **Infer DB Attributes** | Traces | Infers `db.operation.name` and `db.collection.name` from the query. | None. |
| **Extract Attribute** | Traces | Extracts values into a new span attribute. | **Extractions**: a preset (JSON, SQL, or resource path, with a lookup key) or a custom regex with exactly one capture group, and a **New span attribute name**. |
| **Delete Attribute** | Traces, metrics, logs | Deletes attributes from resources, scopes, and records. | **Attributes to delete**. |
| **Rename Attribute** | Traces, metrics, logs | Renames attributes. | **Old key** and **New key**, one pair per **Add rename**. No duplicates, and the old and new keys must differ. |

DB Query Templatization and Infer DB Attributes need the database query text to be collected at the source.

Span Metrics uses the default dimensions `http.method`, `http.request.method`, `http.status_code`,
`http.response.status_code`, `http.route`, and `span.instrumentation.scope.name`, with cumulative temporality.

#### Processor Addition processors

| Processor | Signals |
| --- | --- |
| Attributes, Filter, Transform, Resource, Group by attributes | Traces, metrics, logs |
| Span | Traces |
| Redaction | Traces, logs |
| Probabilistic sampler | Traces, logs |
| Metrics transform, Cumulative to delta, Delta to rate, Metrics generation | Metrics |
| Extract attribute | Traces |

Values such as `${env:...}` and `${file:...}` in the processor JSON are treated literally, not expanded.

### How actions run

- In every destination pipeline, the order is: the Collector's built-in processors (memory limiting,
  resource detection, and `cloud.region`), then your actions, then the destination's own processors, then
  batching.
- You can't control the order among actions. URL Templatization always runs last.
- **Disabled** actions aren't applied.
- Odigos pushes changes to the running Collector. There is no redeploy.

### Limits

<AccordionGroup>
  <Accordion title="One Span Metrics action per region">
    Only one enabled Span Metrics action can run per region, and it needs an active **metrics** destination
    on that Collector. Otherwise it isn't applied, and traces still flow.
  </Accordion>
  <Accordion title="Processor names">
    Two Processor Additions of the same type need different **Processor name** values. A Resource processor
    always needs a name.
  </Accordion>
  <Accordion title="Not supported">
    - PII masking
    - Sampling, other than the probabilistic sampler through Processor Addition
    - Profiles
    - Targeting a single destination
    - Scoping an action by source, service, or language
    - Instrumentation rules
  </Accordion>
</AccordionGroup>

<Warning>
  Actions that conflict with each other or can't be built are **left out**, and the UI doesn't warn you. The
  connector logs a `Collector configuration rendered with a problem` warning naming the action, with a code
  such as `CollectorActionSpanMetricsConflict`, `CollectorActionComponentConflict`, or
  `CollectorActionUnrenderable`.
  If the Collector rejects a configuration, it becomes **Degraded** and keeps running its last accepted
  configuration. Further changes in that region don't take effect until you fix or remove the action.
</Warning>

### Validation errors

| Message | Fix |
| --- | --- |
| `Processor type is required.` | Choose a processor type. |
| `Processor configuration must be valid JSON.` | Fix the JSON syntax. |
| `Processor configuration must be a JSON object.` | Use an object, not an array or a value. |
| `Enable literal templatization or PostgreSQL cast removal` | Turn on at least one option. |
| `At least one row is required` | Add an attribute to delete, a rename, or an extraction. |
| `All row fields are required` | Fill in or remove incomplete rows. |
| `Each rename needs different, non-blank old and new names.` | Make the old and new keys different. |
| `Each row needs a target attribute name and either a regex or both lookup key and data format` | Complete every extraction. |
| `Each new span attribute name must be unique` | Use a different **New span attribute name** for each extraction. |
| `Each rule group needs at least one non-blank template` | Add a template to every rule group. |
| `resource processor additions need a processorName so they do not replace the Collector's built-in resource processor` | Set a **Processor name**. |
| `processor type "<type>" does not support <SIGNAL>` | Select only the signals that processor supports. See [Processor Addition processors](#processor-addition-processors). |
| `extraction regex must contain exactly one capture group` | Use a regex with a single capture group. |
| `region <region> has no Collector; create one first` | Install a Collector in the region. |

## Collector image

By default, Collectors run `registry.odigos.io/odigos-enterprise-collector:<Central version>`. Set the image
with the `cloudConnectors.managedCollectors.collectorImage` Helm value. See
[Managed Collectors](/cloud-connectors/enable#managed-collectors).

- **Upgrading Central** changes the expected image. Automatic Collectors roll to a new task definition
  revision. Manual Collectors show image drift and report **Degraded** until you re-apply the artifacts from
  **Download config**.
- **ECR Public** is supported. Use a `public.ecr.aws/<alias>/<repo>` image. The pull is anonymous, so no
  repository credentials are needed, but the Collector tasks need outbound HTTPS to ECR Public and the
  license and OpAMP secrets are still required.
- **Private ECR** needs the execution role's ECR permissions listed in
  [Install a Collector (automatic)](#install-a-collector-automatic).
- For immutable deployments, reference the image by **digest** rather than by tag.
- A region can override the image with the connector setting `collector.regions.<region>.image`. The setting
  `collector.defaults.image` applies to every region.

## Advanced settings

These per-region Collector settings live in the connector's runtime configuration, next to the image override,
but aren't in the Central UI. Contact Odigos support to set them. Values go under `collector.regions.<region>`,
or under `collector.defaults` to apply to every region. A region value overrides the default.

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `provider.useFargateSpot` | boolean | `false` | Runs the Collector tasks on the `FARGATE_SPOT` capacity provider instead of `FARGATE`. Automatic Collectors only. |
| `rolloutBatchSize` | integer | `10` | The most workloads re-pointed at this Collector per pass. `0` uses the default. See [Cutover behavior](#cutover-behavior). |
| `retention.idleScaleToZeroAfterHours` | integer | `0` (keep) | Scales an idle Collector to zero tasks after this many hours. |
| `retention.idleDeleteAfterHours` | integer | `0` (keep) | Deletes an idle Collector after this many hours. |
| `endpointOverride` | string | none | Publishes your own endpoint to workloads instead of the Odigos-created NLB. |
| `ingress.additionalNetworkIdentityIds` | list of strings | `[]` | AWS security group IDs admitted on TCP 4317 and 4318, in addition to the workload security groups. |
| `ingress.additionalCidrs` | list of strings | `[]` | CIDR ranges admitted on TCP 4317 and 4318, in addition to the workload security groups. |
| `ingress.allowNetworkCidrFallback` | boolean | `true` | Allows the VPC CIDR fallback described in [Install a Collector (automatic)](#install-a-collector-automatic). |
| `ingress.minFallbackPrefixLength` | integer | `16` | Network blocks with a shorter prefix than this are refused by the fallback. `0` uses the default. |
| `tls.mode` | string | `off` | `off` or `loadBalancer`. See [Delivery limits](#delivery-limits). |
| `tls.hostname` | string | none | The hostname you own that points at the NLB. Required for `loadBalancer`. |
| `tls.certificateRef` | string | none | The ACM certificate ARN for the NLB listeners. Required for `loadBalancer`. |
| `logRetentionDays` | integer | `7` | CloudWatch retention for the Collector log group. `0` never expires. Automatic Collectors only. |
| `arch` | string | `amd64` | CPU architecture of the Collector tasks: `amd64` or `arm64`. |

For example, to tune one region and keep 30 days of logs everywhere:

```yaml
collector:
  enabled: true
  defaults:
    logRetentionDays: 30
  regions:
    us-east-1:
      # Keep the region's existing keys, such as networkId and provider.clusterArn.
      rolloutBatchSize: 5
      retention:
        idleScaleToZeroAfterHours: 24
        idleDeleteAfterHours: 168
      ingress:
        additionalNetworkIdentityIds: ["sg-0abc1234"]
        additionalCidrs: ["10.20.0.0/16"]
      provider:
        useFargateSpot: true
```

<Warning>
  The `collector` object is replaced as a whole when it is written, so the change must include every region and
  default that is already set. These keys aren't validated on write: an unknown key or a value of the wrong type
  is ignored and the default applies.
</Warning>

### Notes on these settings

- **Spot.** The cluster you supplied needs the `FARGATE_SPOT` capacity provider associated. Without it, the
  Collector runs on on-demand Fargate and reports **Degraded**. A Spot interruption restarts a task and loses
  its queue. See [Delivery limits](#delivery-limits).
- **Idle retention.** A Collector is idle when its region is disabled or has no enabled sources. The idle clock
  starts the first time Odigos sees it idle and resets when a source returns. By default an idle Collector is
  kept. Scaling to zero stops the tasks and keeps the NLB, security group, and other resources, so re-enabling a
  source is a scale-up. Workloads are routed before the tasks are back, so the first telemetry after that can
  be lost. Deleting removes only what Odigos created, never a manual Collector's resources. If the delete
  time is not longer than the scale-to-zero time, the Collector is deleted without being scaled to zero first.
- **Endpoint override.** Odigos creates no NLB and attaches no load balancer to the service, so you must route
  to the Collector tasks on 4317 and 4318 yourself. Odigos publishes the value as given and doesn't add a port,
  so include it. An `https://` value is treated as encrypted. Setting `tls.mode: loadBalancer` together with an
  override is refused.
- **Extra ingress.** Odigos still removes security group rules you add by hand, so these settings are the way
  to keep a rule. They admit a sender but don't configure it or make it eligible for automatic routing. Setting
  `additionalNetworkIdentityIds` or `additionalCidrs` also means the VPC CIDR fallback is never used, so
  a workload whose security group Odigos can't resolve isn't admitted by it. An invalid CIDR is
  reported as an error and Odigos writes no ingress rules until you fix it. `0.0.0.0/0` and `::/0` are
  refused, and a public range reports **Degraded**. With `allowNetworkCidrFallback: false` and no resolved security group, no ingress is written
  and the Collector isn't deployed.
- **Log retention.** Odigos applies `logRetentionDays` to the log group on every pass, so a change takes effect
  without recreating anything.
- **Architecture.** The Collector image must publish the architecture you choose. Manual installs use it too,
  in the files from **Download config**.

<Note>
  The Central install and edit forms send only the fields they show, and on edit only the ones you changed, so
  editing a Collector in Central leaves these settings alone. Uninstalling a Collector from Central removes
  its `collector.regions.<region>` entry, including these settings, so a reinstall starts from the defaults.
</Note>

## Collector status

Select a region on the Collectors page to see its status badge.

| Status | Meaning |
| --- | --- |
| **Pending**, **Deploying**, **Deleting** | A change is in progress. |
| **Awaiting customer** | Odigos is waiting for you to deploy the Collector (manual mode). |
| **Healthy** | The Collector is ready and connected to Central. |
| **Degraded** | The Collector isn't fully healthy, or it has stopped checking in. |
| **Error** | The last operation failed. |

If a Collector stops checking in, a banner explains the effect:

> This collector has not checked in recently. It may still be exporting, but its configuration can no longer be changed.

The region's overview shows:

| Card | Contents |
| --- | --- |
| Gauges | **CPU** and **Queue depth** |
| **Throughput** | Accepted spans, dropped spans, uptime |
| **Resources** | CPU and memory size, memory in use, and whether the Collector is enabled |
| **Placement** | Execution role, ECS cluster, VPC, public task IP, and subnets (**Selected by Odigos** or **Pinned**) |
| **Runtime** | gRPC and HTTP endpoints, tasks, config, first ready time |
| **Destinations** / **Actions** tabs | The Collector's downstream destinations, and the [actions](#collector-actions) it applies before sending to them |

The action buttons on the overview are **Reconfigure** and **Uninstall**. Use **Refresh** at the top of the
page to reload the status. **Download config** (manual mode only) opens the copyable IaC for the Collector.

### Routing notes

When a workload exports directly instead of through the Collector, its status shows a note that says why.

| Note | Meaning |
| --- | --- |
| `Defaulting to the global OTLP destination: the Odigos Managed Regional Collector has not reported ready yet.` | The Collector hasn't been ready yet. The workload moves once it is. |
| `Defaulting to the global OTLP destination: the Odigos Managed Regional Collector has no ingress endpoint yet.` | The Collector exists, but its load balancer endpoint isn't published yet. |
| `Defaulting to the global OTLP destination: this Lambda has no VPC configuration, so it cannot reach the Odigos Managed Regional Collector. Odigos will not attach the function to a VPC or change its VpcConfig.` | A Lambda function without a VPC. This is permanent by design. |
| `Defaulting to the global OTLP destination: no Odigos Managed Regional Collector is set up in this region.` | The routing destination exists, but this region has no Collector. |
| `Workload VPC <vpc> cannot reach the regional Collector in VPC <vpc>. Verify active same-region VPC peering, reciprocal routes, workload ingress to the NLB, and NLB security-group ingress to Collector tasks on every published OTLP port. ...` | The workload runs in a different VPC from the Collector and Odigos can't confirm the path. See [Which workloads use it](#which-workloads-use-it). |
| `Workload VPC <vpc> shares the Collector VPC, but the Collector ingress security group does not admit this workload on every published OTLP port. ...` | The workload is in the Collector's VPC, but the Collector security group doesn't admit it on 4317 and 4318, or doesn't admit itself on them. |
| `Defaulting to the global OTLP destination: this VPC-attached Lambda cannot currently reach the Odigos Managed Regional Collector. ...` | The same for a VPC-attached Lambda function. The note goes on to list what to fix. |
| `Continuing to use the global OTLP destination until this workload is admitted to the regional Collector rollout.` | The workload is eligible but waiting for its batch. |
| `Cannot export telemetry through the Odigos Managed Regional Collector: <cause>, and no global OTLP destination is configured for fallback.` | There is no global destination, so the workload can't export at all. Fix the cause or add a global destination. |

During a cutover, the Collector reports `N workload cutover(s) in <region> failed and will be retried. Examples: <workloads>.`
when some workloads couldn't be moved yet. The one-minute warning shows as:

> The regional Collector is ready. New workload cutovers are announced and will begin after the one-minute warning window, in bounded batches.

## Delivery limits

Odigos checks DNS, routes, peering, security groups, and network ACLs, but it can't prove end-to-end delivery.
Custom DNS resolvers, middleboxes, and the health of the downstream destination can still stop telemetry.
Confirm telemetry from the workload after the first rollout.

The Collector's queues live on the task's ephemeral storage. A deployment, a Spot interruption, or a task
replacement can lose buffered telemetry. Run at least two on-demand tasks if availability matters. That
improves availability but doesn't make the queues durable.

The Collector can't terminate TLS itself on AWS. To encrypt the hop, set `tls.mode` to `loadBalancer`, which
puts your own ACM certificate on the NLB listeners. It also needs a hostname you own pointed at the NLB.

## Uninstall

Uninstall the Collector while the connector is still running. Uninstall removes the Collector's downstream
destinations and actions and revokes its credentials. It does **not** remove the routing destination of type
**Odigos Managed Regional Collector**. Delete or disable that destination yourself.

Deleting the connector, turning off managed Collectors in Central, or switching the mode to **Off** never
deletes AWS resources. Switching to **Off** revokes the Collector's credentials, and the Collector keeps
running on its last configuration.

<Steps>
  <Step title="Move workloads off the Collector">
    If workloads still need to export telemetry, make sure a global OTLP destination exists, or
    [uninstrument the workloads](/cloud-connectors/instrument-workloads#uninstrument-workloads) first. Without a
    global destination, workloads in the region have nowhere to export once the Collector is gone. When the
    region is disabled, Odigos restores every routed workload to direct export in one pass, not in batches.
  </Step>
  <Step title="Save the resource references">
    The uninstall drawer lists the Collector's cluster, VPC, subnets, service, task definition, load balancer,
    and security group. Copy them before you continue.
  </Step>
  <Step title="Export logs you need">
    Automatic uninstall deletes the Collector's log group. Queued telemetry isn't kept.
  </Step>
</Steps>

### What gets removed

Replace `<region>` with the Collector's region, `<connector>` with the connector name, and `<netid>` with the
VPC ID without its `vpc-` prefix.

| Resource | Automatic uninstall | Manual mode |
| --- | --- | --- |
| ECS service `odigos-collector-<region>` and its running tasks | Removed | You remove it |
| Application Auto Scaling target and policies `odigos-collector-<region>-cpu` and `-memory` | Removed | You remove them (only if scaling is automatic) |
| Internal NLB `odigos-col-<netid>`, its listeners, and target groups `odigos-4317-<netid>` and `odigos-4318-<netid>` | Removed | You remove them |
| Collector security group | Removed when Odigos created it. A group you supplied is never removed | You remove it |
| Secrets `odigos/collector/<connector>/<region>/credential`, `.../credential/bootstrap`, and `.../license` | Removed immediately, with no recovery window. The license secret stays while another Collector in the region uses it | You remove them |
| Log group `/odigos/collector/<connector>` | Removed, unless another Collector in the region uses it | You remove it |
| Task-definition family `odigos-collector-<region>` | **Kept.** Revisions are never deregistered | You remove the revisions |
| Execution role, ECS cluster, VPC, subnets, peering, routes, workload security group rules, and the Application Auto Scaling service-linked role | Kept. They belong to you | Kept |

Odigos deletes an object only when its tags say Odigos created it for this connector **and** Odigos recorded
its reference. Anything else is left in place and listed as retained. In manual mode Odigos deletes nothing.

### Uninstall an automatic Collector

On the region's overview, click **Uninstall**, then **Uninstall collector** in the drawer. Odigos disables the
region and revokes the Collector's credentials first. If it can't revoke them, it deletes nothing. It then
deletes the resources above in dependency order: scaling target, service, load balancer, target groups,
security group, secrets, and log group.

AWS can take several minutes to release the network interfaces that the load balancer and tasks hold. While that
happens the Collector shows **Deleting** and Odigos retries the deletion. If the teardown is still blocked after
30 minutes, the status changes to **Error** and Odigos keeps retrying. Look for the remaining AWS dependency,
and don't remove the connector's finalizer to force it through.

If Odigos did not create the Collector, or has no recorded references, it refuses to delete it and the drawer
says so. Remove the AWS resources with the tool that created them.

When the uninstall finishes, a dialog lists any retained customer infrastructure.

### Uninstall a manual Collector

Remove the AWS resources first with the tool that created them. Then click **Uninstall** on the region's
overview and **Remove from Odigos** in the drawer. That revokes the Collector's credentials and removes its
configuration, destinations, and actions. If you do it first, the Collector keeps running but can no longer
pull its configuration.

<Tabs>
  <Tab title="CloudFormation">
    1. Delete the deployment stack `odigos-collector-<connector>-<region>` and wait for `DELETE_COMPLETE`.
       The stack holds the service, NLB, target groups, and listeners, and the scaling resources if you
       enabled them.
    2. If you used the prerequisites stack, delete `odigos-collector-<connector>-prerequisites`. It holds the
       security group and the log group. Delete it after step 1, once the network interfaces are released.
    3. Remove the secrets you created outside the stacks (see below).
    4. Click **Remove from Odigos**.

    Use the [stack deletion commands](/cloud-connectors/aws/uninstall#use-the-tool-that-owns-the-resource).
    Resolve `DELETE_FAILED` events instead of deleting shared infrastructure to get around a dependency.
  </Tab>
  <Tab title="Terraform / OpenTofu">
    1. In the workspace that created the Collector, review a destroy plan and apply it. If the workspace also
       owns other infrastructure, remove only the Collector resources from the configuration and apply that
       plan.
    2. The generated Terraform doesn't create the security group, log group, secrets, or execution role.
       Remove them with whatever created them, once nothing else uses them.
    3. Click **Remove from Odigos**.

    The [workspace commands](/cloud-connectors/aws/uninstall#use-the-tool-that-owns-the-resource) work for both
    Terraform and OpenTofu. Deleting the state file doesn't remove any infrastructure.
  </Tab>
  <Tab title="AWS CLI / Console">
    Use the values from the drawer. The scalable-target resource ID takes the cluster **name**, not its ARN.

    ```bash
    REGION="<COLLECTOR_REGION>"
    CLUSTER="<CLUSTER_NAME_OR_ARN>"
    CLUSTER_NAME="<CLUSTER_NAME>"
    SERVICE="odigos-collector-$REGION"

    # Only if the service has a scalable target. This removes its scaling policies too.
    aws application-autoscaling deregister-scalable-target --region "$REGION" \
      --service-namespace ecs --scalable-dimension ecs:service:DesiredCount \
      --resource-id "service/$CLUSTER_NAME/$SERVICE"

    aws ecs update-service --region "$REGION" --cluster "$CLUSTER" --service "$SERVICE" --desired-count 0
    aws ecs delete-service --region "$REGION" --cluster "$CLUSTER" --service "$SERVICE"
    aws ecs wait services-inactive --region "$REGION" --cluster "$CLUSTER" --services "$SERVICE"
    ```

    Then:

    1. Delete the internal NLB. Its listeners go with it. Wait for it to be released, then delete the two
       target groups.
    2. Delete the Collector security group once its network interfaces are gone.
    3. Remove the secrets, the log group, and the task-definition revisions (see below).
    4. Click **Remove from Odigos**.

    Keep the ECS cluster and its other services.
  </Tab>
</Tabs>

### Clean up what remains

After either mode, remove these if nothing else uses them.

<Steps>
  <Step title="Task-definition revisions">
    List every revision of the `odigos-collector-<region>` family, including inactive ones, and check that
    nothing runs or schedules them. Deregister the active ones, then delete them:

    ```bash
    TASK_DEFINITION_ARN="<UNUSED_REVISION_ARN>"
    aws ecs deregister-task-definition --region "$REGION" --task-definition "$TASK_DEFINITION_ARN"
    aws ecs delete-task-definitions --region "$REGION" --task-definitions "$TASK_DEFINITION_ARN"
    ```

    An inactive revision only needs the delete call. AWS keeps a revision pending deletion while something
    still references it. See
    [task-definition cleanup](/cloud-connectors/aws/workloads/fargate/instrument#remove-unused-task-definition-revisions).
  </Step>
  <Step title="Manual secrets and log group">
    For secrets you created, pick a recovery window:

    ```bash
    aws secretsmanager delete-secret --region "$REGION" \
      --secret-id "<SECRET_ARN>" --recovery-window-in-days 7
    ```

    A secret with a recovery window is only scheduled for deletion. Don't delete a license secret or log group
    that another Collector in the region still uses. Deleting the log group permanently removes its logs.
  </Step>
  <Step title="Execution role">
    Remove the role and its inline policy, but only after every region that uses it is gone. Odigos never owns
    it. If you deployed it from the wizard's CloudFormation template, delete the stack
    `odigos-collector-<connector>-execution`. Otherwise use Terraform state or IAM.
  </Step>
  <Step title="Network additions">
    Remove the workload security-group rules, peering connections, routes, DNS records, ACM certificate, and
    private image mirror that you added for the Collector. Keep shared ones.
  </Step>
  <Step title="Routing destination">
    Delete or disable the **Odigos Managed Regional Collector** routing destination for the region.
  </Step>
</Steps>

To check the result, confirm that the region has no Collector tasks, service, scaling target, NLB, target
groups, or dedicated security group, and that secrets and logs are deleted or recorded as pending. Compare
the retained-resource list from Odigos with what you see in AWS.
